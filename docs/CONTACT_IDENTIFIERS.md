# LMT identifiers and enquiry arrival dates

Contact IDs use `LMT-C-000042`. Enquiry IDs include the first branch: `LMT-KN-L-000099` (Kalyan Nagar), `LMT-MT-L-000100` (Marathahalli), or `LMT-BTM-L-000101` (BTM Layout). Numeric suffixes still use the global sequence; they are not restarted per branch. An ID and its recorded origin branch never change during reassignment or transfer. The current assigned branch is shown separately. A contact may have several course enquiries with separate IDs and arrival dates. Contact IDs identify the person in mobile/Google Contacts. Google Contacts synchronization is available after OAuth setup; see [Google Contacts setup](GOOGLE_CONTACTS.md).

The controlled `common.0005_branch_enquiry_ids` migration preserves numeric suffixes and stores the previous flat enquiry ID as a search alias. It uses the earliest assignment history's previous branch as origin. If assignment history is unavailable, it uses the current branch and labels that origin as unverified rather than inventing a transfer history. Branch codes are frozen on the enquiry even if branch configuration is renamed later. PostgreSQL guards protect the enquiry ID, origin branch and origin code. UUIDs, contact links and existing enquiry URLs are unchanged.

The controlled `common.0004_lmt_ids_and_received_dates` migration converts existing `LM-C-…` and `LM-L-…` IDs to LMT while preserving numeric suffixes, UUIDs and relationships. It checks collisions before changing IDs. PostgreSQL briefly takes table locks and reinstalls ID-protection triggers within the same atomic migration. Run deployment migrations while intake is paused. The local SQLite database was backed up before applying this change. Historic audit text is not rewritten. Contact, enquiry and inbox searches accept old LM IDs as aliases.

Each enquiry exposes read-only `received_at` and `received_via`. New WhatsApp intake records the triggering message time; delayed identity resolution uses the earliest recorded inbound message. Website intake records the saved webhook receipt time. Calls use the original call start time even when a lead is created later. Manual enquiries use CRM creation time. Linking an existing enquiry preserves its first-received timestamp; a deliberately new course enquiry gets its own timestamp. The system does not infer a new course's arrival date from free-text chat.

For pre-existing enquiries, call and website evidence is used where available; otherwise CRM creation is the honest fallback, labelled `crm_recorded`. Unknown historic arrival dates are not invented. Contact `first_enquiry_at` is the earliest recorded arrival among enquiries visible to the viewer, so dates do not disclose hidden branch activity. Enquiry detail, contact profile, communication-history ownership cards and linked WhatsApp ownership cards display dates in IST.
